# WTAnalyzer — Planning Document

> Companion analyzer plugin for WTSynth-driven effect testing.
> Author: Fine Increments. Collaborator: Shane Dunne (author of WTSynth).
> Last updated: 2026-05-13.

## 1. What this plugin is

WTAnalyzer is a JUCE-based VST3/AU plugin that **measures how an audio effect responds to a known test signal generated by WTSynth**. It sits downstream of the effect being tested in a DAW's audio graph, captures pre- and post-effect audio, and produces diagnostic visualizations: frequency response, harmonic distortion, intermodulation, aliasing, step response, impulse response, and others.

The conceptual pairing:

| Plugin | Role |
|---|---|
| **WTSynth** (Shane Dunne) | Loads a Python-generated wavetable, plays it through the synth engine. Provides the *test signal*. |
| **WTAnalyzer** (Fine Increments) | Sits after the effect under test, receives both raw and processed signal, computes per-mode analyses. |

Together they form a **two-plugin DSP test bench** that lives inside the DAW, alongside the effect being developed. The signal palette is determined by a set of Python scripts (e.g. `sweep.py`, `harmonics.py`, `chirp.py`, `multisine.py`, `two_tone.py`, `noise.py`, `step.py`, `impulse.py`, `pwm.py`) that produce wavetables encoding specific diagnostic signals.

## 2. What WTSynth is and how we use it

### 2.1 What WTSynth is

WTSynth is a wavetable synthesizer plugin (VST3/AU) written by Shane Dunne. Its distinguishing feature is a built-in **Python script runner**: the user picks a `.py` file via "Select Script…", and WTSynth invokes it via the command line with parameters from a `.xml` UI specification, producing a `wavetable.wav` that the synth's oscillator then plays.

The plugin's UI has the following sections:

| Section | Controls | Purpose |
|---|---|---|
| **Master** | Level, PB.Up, PB.Dn | Output gain, pitch-bend ranges |
| **LFO** | Waveform (Triangle/Sine/etc), Uni/Bi, Rate, Depth | Low-frequency modulator |
| **Oscillator** | Reset WT, Load WT, **WT Pos**, Phases, Detune, Width, +/− buttons | Wavetable selection & playback |
| **Filter** | Type (OFF / LP / HP / etc), Slope, Cutoff, Res, Env Amt, ADSR | Optional filtering |
| **Amplifier** | ADSR | Volume envelope per note |
| **Python Script** | Select Script…, Run Script, dynamic parameter UI | Wavetable generation pipeline |

The Python pipeline:

1. User clicks "Select Script…", picks e.g. `chirp.py`.
2. WTSynth reads `chirp.xml` next to it and renders a parameter UI from that XML.
3. User adjusts parameters, clicks "Run Script".
4. WTSynth invokes `python chirp.py <param1> <param2> ... <num_frames> <output_folder>`.
5. The script writes `wavetable.wav` into the output folder.
6. WTSynth loads that WAV as its current oscillator wavetable.

The `wavetable.wav` Shane confirmed supports: integer PCM at any bit depth, or 32-bit float, mono, 2048 samples per frame, any number of frames concatenated. Our scripts emit float WAV at 48 kHz, 2048 samples per frame.

### 2.2 What WTAnalyzer uses, and what it ignores

For test-tone generation we want a **pristine, unprocessed signal** at the synth's output — the wavetable as written, played as-is. The Filter, LFO, and envelope sections of WTSynth all *color* or *shape* the signal, which would contaminate any analysis we run on the post-effect side. So:

| Section | WTAnalyzer's interest |
|---|---|
| Master Level | Set to unity (or any consistent gain). Doesn't affect signal shape. |
| Master PB.Up/PB.Dn | Irrelevant — we don't bend pitch during tests. |
| LFO | **Disable** (set Depth to 0). Any modulation would interfere with measurements. |
| **Oscillator → WT Pos** | **Primary control.** This is the wavetable-position-as-sweep-axis. We sweep this via DAW automation. |
| Oscillator → Phases | Set to single-voice / minimum, to avoid voice phase confounds. |
| Oscillator → Detune | Set to 0. No detuning artifacts. |
| Oscillator → Width | Set to 0 (mono). Analysis is mono. |
| Filter | **Disable** (Type = OFF, already the default). We don't want WTSynth filtering before the device under test. |
| Filter ADSR / Env Amt | N/A while filter is off. |
| Amplifier ADSR | Set to instant attack, full sustain, instant release (A=0, D=0, S=max, R=0). Gives an on/off envelope that doesn't shape transients. |

The recommended "neutral preset" for WTSynth when used with WTAnalyzer:

```
Master:     Level=unity, PB.Up=0, PB.Dn=0
LFO:        Depth=0 (rate doesn't matter)
Oscillator: Phases=1, Detune=0, Width=0; WT Pos is the swept variable
Filter:     OFF
Amplifier:  A=0, D=0, S=max, R=0
```

We should consider shipping a saved WTSynth preset file with WTAnalyzer that loads this configuration in one click. (Open question: WTSynth's preset format and whether one can be distributed as a single file.)

### 2.3 How WTAnalyzer integrates with WTSynth

The integration is **file-mediated, not API-mediated.** WTSynth generates a wavetable file on disk; WTAnalyzer reads that file as its reference. No inter-plugin IPC, no shared memory, no Python invocation from inside the analyzer.

Shane's architectural recommendations (which we accepted):

1. **Load `wavetable.wav` directly** — the file is the contract, not the script that produced it.
2. **Use AudioProcessorGraph multi-bus** — pre-effect and post-effect signals arrive on separate input buses, routed by the host, sample-aligned.
3. The analyzer doesn't need to run Python or know about scripts at runtime.

### 2.4 Script picker for analysis selection and parameter discovery

WTAnalyzer exposes a **"Select Script…"** button mirroring WTSynth's UI. When the user picks a `.py` file, WTAnalyzer:

1. Reads the matching `<scriptname>.xml` sibling file (e.g., `chirp.py` → `chirp.xml`).
2. Parses the XML to discover the script's parameters (types, ranges, defaults, choice options) AND its `analysis="…"` attribute, which declares which built-in analysis method this script's output is intended to feed (see §2.6).
3. Builds a parameter UI inside WTAnalyzer that mirrors what WTSynth shows for the same script.
4. Selects the matching analysis mode based on the declared analysis (see §4).
5. If a `wavetable.json` sidecar exists in the same folder, pre-fills the parameter UI with the values from the most recent run (see §2.5).

This is the **mode-and-shape** half of the integration. It tells WTAnalyzer what the test signal is and what parameters were available. By itself, it doesn't tell WTAnalyzer *which values were chosen* in the most recent run — for that, see §2.5.

#### Why the picker exists alongside the sidecar JSON

The two mechanisms answer different questions:

| Layer | Source | What it provides |
|---|---|---|
| Script picker + `.xml` parsing | Static script file + sibling XML | Mode identification, parameter UI structure |
| Sidecar JSON (§2.5) | Written by the script at run time | The actual values used in the most recent run |

Together they cover every case:

- **Modified script + recent run:** picker identifies the mode, sidecar fills in the values → fully automatic.
- **Unmodified script (no sidecar):** picker still identifies the mode and builds the UI; user enters values manually to match what they used in WTSynth.
- **Custom user-authored script:** picker reads its XML and builds a UI; if there's a registered analysis mode for that script's name, great; otherwise the user picks a generic mode.

#### XML parsing details

The XML schema is WTSynth's existing one, with **one additive attribute**: `analysis="…"` on the root `<ParameterSet>` element. WTSynth ignores unknown attributes, so adding `analysis` is backwards-compatible — WTSynth still reads the same XML; WTAnalyzer reads the extra attribute.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<ParameterSet analysis="FarinaDeconvolution">
  <Choice name="Type" minVal="0" maxVal="1" defaultVal="1">
    <Item String="Linear"/>
    <Item String="Log (Farina)"/>
  </Choice>
  <Int name="Start" minVal="1" maxVal="64" defaultVal="1"/>
  <Int name="End" minVal="2" maxVal="1024" defaultVal="256"/>
  <Int name="#Frames" minVal="2" maxVal="256" defaultVal="32"/>
</ParameterSet>
```

The `analysis` attribute names one of WTAnalyzer's built-in analysis methods (see §2.6). If absent or unrecognized, the analyzer pops up an analysis-selection dialog asking the user to pick one (see §2.7 for the full fallback ladder).

Supported parameter elements: `Choice` (with nested `Item` children for the dropdown), `Int`, `Float`, `Bool`. JUCE's `juce::XmlDocument` parses this in ~10 lines.

The parameter UI in WTAnalyzer renders:

- `Choice` → combobox / dropdown
- `Int` → integer slider or spinbox
- `Float` → float slider
- `Bool` → checkbox

Layout adapts to however many parameters the XML declares.

### 2.5 Exact parameter capture — without changing WTSynth

The picker (§2.4) tells WTAnalyzer *which* script was used and *what parameters exist* for it. The remaining piece is *what values were chosen* in the most recent WTSynth run. The picker can't determine that from static files alone — the `.xml` only has defaults.

**WTSynth does not currently emit any metadata about parameter values.** Asking Shane to add this would be a feature request on his side. We don't need to.

**The plan: our Python scripts emit the values themselves.** Each script (`sweep.py`, `chirp.py`, `harmonics.py`, etc.) already receives its parameters on the command line. We modify each script to write a sidecar JSON file alongside the WAV it produces. When WTAnalyzer opens that folder, it reads the JSON and pre-fills the parameter UI built by the picker.

#### Sidecar JSON format

Filename: `wavetable.json` (same folder, same base name as the WAV).

Schema:

```json
{
  "schema_version": 1,
  "script": "chirp.py",
  "analysis": "FarinaDeconvolution",
  "generated_at": "2026-05-10T20:30:00Z",
  "audio": {
    "sample_rate": 48000,
    "samples_per_frame": 2048,
    "frame_count": 32,
    "format": "float32",
    "channels": 1
  },
  "parameters": {
    "Type": "Log (Farina)",
    "Start": 1,
    "End": 256,
    "#Frames": 32
  },
  "command_line": ["chirp.py", "Log (Farina)", "1", "256", "32", "/path/to/output"]
}
```

Field meanings:

- `schema_version`: bump if we ever change the structure.
- `script`: filename of the generator. Informational; the picker / analyzer doesn't strictly need it.
- `analysis`: which analysis method the script is intended to feed (see §2.6 for the registry). The analyzer uses this to select the mode. Mirrors the `analysis="…"` attribute in the script's `.xml`.
- `generated_at`: ISO 8601 timestamp; lets the analyzer detect stale JSON vs. WAV mismatch.
- `audio.*`: redundant with the WAV header but easier to read.
- `parameters`: the actual values used. Keys match the `<param name="…">` in the script's `.xml`. Values are typed (string for Choice, int for Int, float for Float, bool for Bool).
- `command_line`: the raw arguments, in case anything was unexpected.

#### How the analyzer consumes it

1. User picks a script via the picker (§2.4) → analyzer identifies the analysis mode and builds the parameter UI.
2. Analyzer looks for `wavetable.json` in the same folder.
3. If JSON is present, its `parameters` block pre-fills the UI values; the `script` field is cross-checked against the picked script (mismatch → warning).
4. Analyzer applies the values to configure the selected mode (e.g., for Farina: synthesize the inverse sweep using Start/End/Type; for two-tone: pull A and B harmonic numbers; for multisine: build the expected bin list from MaxHarmonic).
5. If JSON is missing or malformed, analyzer falls back to `.xml` defaults and lets the user enter values manually.

#### Why this works

- **No Shane-side changes.** WTSynth invokes the script the same way it always did. The script's behavior is what changed.
- **No Python at runtime in WTAnalyzer.** The analyzer just reads JSON.
- **Self-describing artifacts.** The WAV + JSON pair fully captures what was generated. They can be shared, archived, or replayed without context.
- **Backwards-compatible.** Older WAVs without sidecar JSON still work — analyzer just asks the user which mode to use.
- **Extensible.** New scripts plug in by writing the same JSON shape. We control the schema.

#### Implementation cost on the script side

Trivial. A shared helper function `write_sidecar(output_path, script_name, params, frame_count)` added to each script. We can factor it into a `wt_common.py` module shared across all scripts, since they all do the same thing.

Estimated effort: one afternoon to update all nine scripts and verify each one writes valid JSON next to its WAV.

### 2.6 The analysis registry (semantic types)

**Key framing decision:** WTAnalyzer's semantics are organized around the **analysis methods** it implements, not around the signal types it might encounter. The set of analyses is fixed by WTAnalyzer's code; signals are inputs that opt into a particular analysis. This is more honest than a "signal-type" framing, because adding a new signal type to WTSynth via a Python script *cannot* automatically create new analysis code in WTAnalyzer — only matching against an existing analysis is possible.

A script declares which analysis its output is intended to feed via the `analysis="…"` attribute in its `.xml`.

#### Built-in analysis methods

| Analysis ID | What it measures | Required signal shape |
|---|---|---|
| `FrequencyResponse` | Magnitude + phase response across frequency | Pure sine per frame (one harmonic at a time) |
| `THDMeasurement` | Total harmonic distortion + per-harmonic breakdown | Single sine, ideally swept across frames |
| `IMDMeasurement` | Intermodulation distortion products at A±B, 2A−B, 2B−A, etc. | Two simultaneous sines |
| `FarinaDeconvolution` | Linear IR + separated harmonic-distortion IRs | Log-frequency chirp with known sweep params |
| `MultisineFlatness` | Flat-spectrum response + off-bin distortion floor | Sum of equal-amplitude harmonics with known phases |
| `ImpulseResponse` | Filter IR, decay time, ringing | Sparse impulse(s) per cycle |
| `StepResponse` | Transient response, overshoot, settling time | Step transition within a cycle |
| `AliasingDetection` | Folded artifacts from non-band-limited processing | Band-limited harmonic series with controlled max harmonic |
| `TransferFunctionFromNoise` | Effect's transfer function via spectral ratio | Colored noise with known slope |
| `GenericOverlay` | Universal overlays only (pre/post spectrum, difference, transfer) | Anything (default / fallback) |

Adding a new analysis is a WTAnalyzer code change (new mode implementation + UI). Adding a new signal that fits an existing analysis is only a script change (or a user authoring their own script).

#### Required parameter names per analysis

Each analysis reads specific well-known parameter names from the captured values to configure itself. To enable a given analysis, a script needs to expose those names. Other parameters are fine — they just don't influence analysis math.

| Analysis ID | Required parameter names | What they're used for |
|---|---|---|
| `FrequencyResponse` | (none required) | Derives fundamental from FFT peak |
| `THDMeasurement` | (none required) | Detects fundamental, sums harmonic bins |
| `IMDMeasurement` | `Lower`, `Upper` | The two harmonic indices for IMD products |
| `FarinaDeconvolution` | `Type` (Linear/Log), `Start`, `End` | Synthesize the inverse sweep for deconvolution |
| `MultisineFlatness` | `MaxHarmonic` (and optionally `Phase`) | Build the expected bin list; off-bins = distortion |
| `ImpulseResponse` | `Position` (optional) | Time-align IR if impulse isn't at sample 0 |
| `StepResponse` | `Mode` (optional) | Distinguish naive step vs. band-limited |
| `AliasingDetection` | `Shape`, `Start`, `End` | Which harmonics are expected; everything else is alias |
| `TransferFunctionFromNoise` | `Color` | Pre-flatten the expected spectral slope |
| `GenericOverlay` | (none) | No analysis-specific config |

Missing parameters degrade gracefully: the analyzer runs whatever subset of the analysis is possible and notes what's missing in the UI.

#### What this means for our nine existing scripts

All nine already have signal shapes that fit a built-in analysis. The mapping:

| Script | Declared analysis | XML edit needed |
|---|---|---|
| `sweep.py` | `FrequencyResponse` | Add `analysis="FrequencyResponse"` |
| `pwm.py` | `GenericOverlay` | Add `analysis="GenericOverlay"` |
| `two_tone.py` | `IMDMeasurement` | Add `analysis="IMDMeasurement"` |
| `impulse.py` | `ImpulseResponse` | Add `analysis="ImpulseResponse"` |
| `chirp.py` | `FarinaDeconvolution` (when Type=Log) or `FrequencyResponse` (when Type=Linear) | Add `analysis="FarinaDeconvolution"`; analyzer reads `Type` to switch behavior |
| `multisine.py` | `MultisineFlatness` | Add `analysis="MultisineFlatness"` |
| `noise.py` | `TransferFunctionFromNoise` | Add `analysis="TransferFunctionFromNoise"` |
| `harmonics.py` | `AliasingDetection` | Add `analysis="AliasingDetection"` |
| `step.py` | `StepResponse` | Add `analysis="StepResponse"` |

A one-line XML edit per script. WTSynth still reads them the same way.

#### What this means for user-authored scripts

A user writes `my_chirp_variant.py` and a matching `my_chirp_variant.xml`. They can:

- **Reuse an existing analysis** by declaring `analysis="FarinaDeconvolution"` (or whatever fits) and exposing the required parameter names. Their script gets the full Farina view in WTAnalyzer with no code changes on our side.
- **Fall back to generic** by declaring `analysis="GenericOverlay"` (or omitting the attribute). They get the universal overlays.
- **Get a new analysis** only if someone writes the analysis code in WTAnalyzer. The architecture doesn't prevent this — adding an analysis is a known extension point — but it's a code change, not a script-only change.

This is the honest contract: **users opt into existing analyses; new analyses require analyzer-side code.**

#### Flexibility within WTSynth's parameter schema

WTSynth's `.xml` supports `Choice`, `Int`, `Float`, `Bool`. Any future script using those four types, in any combination, with any names/ranges/defaults, will be discoverable by the picker, renderable into a UI, and capturable into the sidecar JSON. This is a constraint set by WTSynth, not by us. The only thing the script must additionally do to opt into a specific analysis is name well-known parameters per the required-names table above.

### 2.7 Script authoring convention

This section is the canonical reference for anyone writing a new script intended to work with WTAnalyzer (including us, when we update the existing nine).

#### Required (for WTSynth, inherited)

1. A runnable Python script (`<name>.py`).
2. CLI signature: positional args, with the **last two always** being `<num_frames> <output_folder>`. Script-specific params come first, in the order they appear in the XML.
3. The script writes `wavetable.wav` into the output folder. Mono, 2048 samples per frame, frames concatenated. Bit depth: int (any) or float — WTSynth reads both.
4. A sibling `<name>.xml` describing the parameter UI. Root element `<ParameterSet>`. Child elements: `<Choice>` (with nested `<Item String="…"/>`), `<Int>`, `<Float>`, `<Bool>`, each with `name`, `minVal`, `maxVal`, `defaultVal` attributes.

If you only do this much, the script works in WTSynth normally and shows up in WTAnalyzer's picker. WTAnalyzer will prompt for analysis selection (see below) but can't auto-configure values.

#### Recommended (for WTAnalyzer integration)

5. **Declare the analysis** on the `<ParameterSet>` root:
   ```xml
   <ParameterSet analysis="FarinaDeconvolution">
   ```
   Pick the matching ID from §2.6's registry. If you can't find one that fits, declare `analysis="GenericOverlay"` to opt out explicitly. WTSynth ignores unknown attributes, so adding this is backwards-compatible.

6. **Use the well-known parameter names** for your chosen analysis (§2.6 required-parameters table). These are the names the analysis math looks up. Extra parameters with custom names are fine and ignored by the analyzer.

7. **Write a sidecar JSON** (`wavetable.json`) next to the WAV, with the schema in §2.5. Captures the actual parameter values used in the run, so WTAnalyzer can pre-fill its UI without manual re-entry.

Doing all of (5), (6), and (7) makes the script fully automatic in WTAnalyzer — pick the script, everything else auto-configures.

#### What happens when pieces are missing

A tiered fallback ladder, with explicit user prompts (not silent degradation):

| Missing | Behavior |
|---|---|
| `.xml` file | Picker can't build a parameter UI. User must manually pick analysis and enter parameters. Show warning: "No XML found for this script — manual configuration required." |
| `analysis="…"` attribute on `<ParameterSet>` | **Pop up a dialog** listing all analyses and ask the user to pick. Checkbox: "Remember for this script." If checked, the choice is saved in WTAnalyzer's per-user override store (see below) so the prompt doesn't re-appear. |
| Sidecar `wavetable.json` | Picker still builds the parameter UI from the `.xml`. Fields show the `.xml` defaults; user manually enters the values to match WTSynth. Optional warning chip: "No sidecar JSON — values may not match WTSynth's last run." |
| Some required parameter names (per analysis) | Analyzer runs whatever subset of the analysis is possible, displays a status line noting what couldn't be computed (e.g., "Farina deconvolution unavailable — missing Start/End parameters"). |
| `wavetable.wav` itself | Hard error. Nothing to analyze. Display a clear message and instructions to run WTSynth's script first. |

This way the user always knows *why* an analysis isn't available and what to do about it.

#### Per-user analysis override store

When the user picks an analysis for a script that didn't declare one (via the pop-up), and they check "Remember for this script," WTAnalyzer saves the choice to a config file:

- Path: `~/Library/Application Support/WTAnalyzer/script_analysis_overrides.json` (macOS) / equivalent on other platforms
- Format: `{ "<script_filename_or_path>": "<AnalysisID>", … }`
- Used as the analysis source whenever the XML doesn't declare one
- User can also override an XML-declared analysis here, in case they disagree with the script author's choice

The plugin's settings UI exposes a "Manage script analysis overrides" panel where users can edit, clear, or reset these entries.

#### Why the prompt instead of silent fallback

Analysis selection is too important to default-and-hope. The whole product hinges on choosing the right analysis for the input. If a script lacks the declaration:

- Silent fallback to `GenericOverlay` would make WTAnalyzer feel broken ("why are my IMD measurements missing?") without telling the user it's a script-author oversight.
- An explicit prompt makes the relationship visible: "this script didn't say what kind of test it is — what do you want to do with it?"
- The remembered override means the prompt only appears once per script, not every time the user reloads.

#### Minimal script example

A bare minimum WTAnalyzer-ready script. For a hypothetical "single-cycle white noise burst" test signal:

`noise_burst.py`:
```python
import os
import sys
import numpy as np
import soundfile as sf
import json
from datetime import datetime, timezone

SAMPLES_PER_FRAME = 2048
SAMPLE_RATE_HZ = 48000

amplitude = float(sys.argv[1])
seed_start = int(sys.argv[2])
num_frames = int(sys.argv[3])
output_path = sys.argv[4]

frames = []
for i in range(num_frames):
    rng = np.random.default_rng(seed_start + i)
    frame = amplitude * rng.uniform(-1.0, 1.0, SAMPLES_PER_FRAME)
    frames.append(frame.astype(np.float32))

data = np.concatenate(frames)
sf.write(os.path.join(output_path, "wavetable.wav"), data, SAMPLE_RATE_HZ, subtype="FLOAT")

sidecar = {
    "schema_version": 1,
    "script": "noise_burst.py",
    "analysis": "TransferFunctionFromNoise",
    "generated_at": datetime.now(timezone.utc).isoformat(),
    "audio": {
        "sample_rate": SAMPLE_RATE_HZ,
        "samples_per_frame": SAMPLES_PER_FRAME,
        "frame_count": num_frames,
        "format": "float32",
        "channels": 1,
    },
    "parameters": {
        "Amplitude": amplitude,
        "Seed Start": seed_start,
        "#Frames": num_frames,
    },
    "command_line": sys.argv,
}
with open(os.path.join(output_path, "wavetable.json"), "w") as f:
    json.dump(sidecar, f, indent=2)
```

`noise_burst.xml`:
```xml
<?xml version="1.0" encoding="UTF-8"?>
<ParameterSet analysis="TransferFunctionFromNoise">
  <Float name="Amplitude" minVal="0.0" maxVal="1.0" defaultVal="0.5"/>
  <Int name="Seed Start" minVal="0" maxVal="9999" defaultVal="0"/>
  <Int name="#Frames" minVal="2" maxVal="256" defaultVal="32"/>
</ParameterSet>
```

That's the entire surface area of a fully-compatible script. Sixty lines, two files, and the analyzer auto-configures itself when this script's wavetable is loaded.

#### Shared helper for sidecar writing

We'll factor the JSON-writing block into a small shared module (`wt_common.py`) so each script reduces to one function call:

```python
from wt_common import write_sidecar

write_sidecar(
    output_path,
    script_name="noise_burst.py",
    analysis="TransferFunctionFromNoise",
    audio={"sample_rate": SAMPLE_RATE_HZ, "samples_per_frame": SAMPLES_PER_FRAME, "frame_count": num_frames, "format": "float32", "channels": 1},
    parameters={"Amplitude": amplitude, "Seed Start": seed_start, "#Frames": num_frames},
    argv=sys.argv,
)
```

The helper handles timestamp, schema_version, and JSON serialization. Lives in `WTSynth_Scripts/wt_common.py`.

## 3. Architecture

### Plugin shape

- **Two stereo input buses (bus 0 = main, bus 1 = sidechain in VST3/AU):**
  - Bus 0 — "Post-Effect" (main input): what's flowing through the effect chain at the point where WTAnalyzer sits. With the plugin placed at the end of the effect chain on the same track (the canonical Ableton workflow), this is the wet/post-effect signal.
  - Bus 1 — "Pre-Effect" (sidechain input): the dry signal *before* the effect under test, routed in via the host's sidechain UI ("Audio From → …" in Ableton, sidechain menu in Logic, etc.). Optional during initial wiring — the plugin loads with bus 1 disabled and only activates the pre-effect comparison once the user wires it.
- **One stereo output bus:** pass-through of bus 0 (Post-Effect), so the track's audio continues downstream as the user expects (the processed signal, not the dry sidechain).
- **Host context:** Any VST3/AU host that supports sidechain input routing — virtually every modern DAW (Ableton Live, Logic Pro, Reaper, Cubase, Bitwig, Studio One, Pro Tools, FL Studio) plus graph hosts (Unify, Gig Performer, JUCE AudioPluginHost). JUCE maps the plugin's second input bus to the format-native sidechain bus in VST3 and AU automatically; users route the post-effect signal into it via each DAW's existing sidechain UI ("Audio From → …" in Ableton, sidechain menu in Logic, etc.). **Primary daily-driver test target: Ableton Live** — anything that works there is expected to work in the other modern DAWs with minor routing variations. AudioPluginHost is used as a fast dev-iteration loop, not as a target platform.

### Constructor wire-up (target)

```cpp
WTAnalyzerAudioProcessor::WTAnalyzerAudioProcessor()
    : AudioProcessor (BusesProperties()
        .withInput  ("Post-Effect", juce::AudioChannelSet::stereo(), true)  // main
        .withInput  ("Pre-Effect",  juce::AudioChannelSet::stereo(), true)  // sidechain
        .withOutput ("Output",      juce::AudioChannelSet::stereo(), true))
{
}
```

`isBusesLayoutSupported` requires stereo on bus 0 and stereo-or-disabled on bus 1 (sidechain may be unrouted during initial setup); everything else rejected.

### Reference-file path

The analyzer reads `wavetable.wav` from a user-configured folder (default: WTSynth's script output folder). The file's structure is known:

- 2048 samples per frame
- Float WAV (32-bit IEEE) — the upgraded format Shane confirmed WTSynth supports
- Mono
- Sample rate 48000 Hz
- N frames concatenated

Frame count is derived from file size. Per-frame content can be sliced for cross-correlation against incoming audio (position inference, v2).

## 4. Analysis modes (per source signal type)

WTAnalyzer's mode selector lists the analysis methods defined in the §2.6 registry. The math each analysis performs and the example script that targets it:

| Analysis ID | Math | Example source script(s) | Primary metric |
|---|---|---|---|
| `FrequencyResponse` | FFT pre + post, divide bin-by-bin | `sweep.py`, `chirp.py` (Linear) | Magnitude + phase response |
| `THDMeasurement` | FFT output, sum harmonic bins relative to fundamental | `sweep.py` (per frame) | THD total + per-harmonic |
| `IMDMeasurement` | FFT output, flag energy at non-fundamental locations | `two_tone.py` | IMD products, IMD% |
| `FarinaDeconvolution` | Convolve output with inverse log sweep | `chirp.py` (Log/Farina) | Linear IR + separated distortion IRs |
| `MultisineFlatness` | FFT output at known multisine bins; check off-bin floor | `multisine.py` | Flat-spectrum response + distortion floor |
| `ImpulseResponse` | Output cycle IS the IR (time-aligned) | `impulse.py` | IR shape, decay time, RT60-style metrics |
| `StepResponse` | Time-domain output of a step transition | `step.py` | Ringing, overshoot, settling |
| `AliasingDetection` | FFT output, flag energy at frequencies not in expected harmonic set | `harmonics.py` | Aliasing onset (vs. position), total alias energy |
| `TransferFunctionFromNoise` | Welch's method on input + output, spectral ratio | `noise.py` | Transfer function magnitude + phase |
| `GenericOverlay` | Universal overlays only | `pwm.py`, any unrecognized script | Pre/post spectrum, difference, transfer |

### Universal overlays (mode-independent)

Available in any mode as togglable layers:

- **Pre/post spectrum overlay** — two FFT traces superimposed
- **Difference signal** — `post − pre` after latency compensation
- **Transfer function** — `post / pre` per bin
- **Reference curve** — a frozen snapshot for A/B
- **Latency readout** — measured effect delay

## 6. Sweep position handling

Most of the diagnostic scripts encode their interesting axis along **wavetable frame position**. WTAnalyzer must associate each captured audio moment with the position value it came from.

### Decision: use shared DAW automation

Shane proposed (and we agreed): WTSynth's Position parameter and WTAnalyzer's "Sweep Position" parameter both expose 0–1 normalized values. The user creates one DAW automation lane / macro that drives both simultaneously. The analyzer's cursor stays in lockstep with WTSynth without any inter-plugin communication.

This also **generalizes to parameter sweeps** (Plugin-Doctor-style). See §6.1 for the full treatment.

### 6.1 Parameter sweeps (Plugin-Doctor-style, via DAW automation)

Shane's "shared DAW automation drives both plugins" trick is more general than just tracking wavetable position. The same mechanism enables an entire class of test — sweep an effect's *own* parameters while holding the input signal static — which is the bread-and-butter measurement style of tools like Plugin Doctor.

#### Two distinct sweep styles

| Style | What varies | What stays fixed | Measures |
|---|---|---|---|
| **Test-signal sweep** | WTSynth's wavetable position (input character) | The effect's parameters | How the device responds to different inputs |
| **Parameter sweep** | A parameter on the effect under test | The input signal (WTSynth stays on one frame) | How the device's response changes as its own parameter changes |

Both are useful for different questions. Plugin Doctor only does the second style natively. We can do both because the mechanism is the same.

#### The architecture that makes this possible

The analyzer exposes one parameter — **Sweep Position**, range 0–1 — and **doesn't care what's being swept on the other side of the automation link**. It just plots `metric(t)` against `SweepPos(t)`. The user wires the DAW automation to drive:

- WTSynth's Position parameter → test-signal sweep
- The effect-under-test's parameter (e.g. Cutoff) → parameter sweep
- Multiple targets in lockstep → compound sweep (rarely useful)
- Anything else the DAW can automate → user-defined sweep axes

This is a more powerful abstraction than Plugin Doctor's built-in parameter sweep, because the user defines what the sweep variable *is*. The cost is having to set up DAW automation manually instead of clicking a dropdown.

#### What the analyzer needs to support this

Minimal additions to the existing design:

1. **A "Sweep Position" automatable parameter** in 0–1 — already on the v1 design.
2. **Capture mode** that records `(SweepPos, measurement)` pairs across a full automation pass — already planned (offline sweep capture, v1).
3. **User-provided axis labels** — a small text field where the user types "Sweep 0–1 corresponds to Cutoff 20 Hz – 20 kHz, log" so the plot's X axis can show meaningful values. The analyzer doesn't read the plugin-under-test's parameter directly; the label is informational.

That's it. No new architectural work — parameter sweep mode is essentially the same code path as test-signal sweep mode, with different DAW routing on the user's side.

#### Differences from Plugin Doctor's parameter sweep

| Aspect | Plugin Doctor | WTAnalyzer |
|---|---|---|
| Sweep speed | Step-and-measure, can be near-instant | Real-time only (10 s sweep takes 10 s) |
| Density | Can do thousands of measurement points | Limited by sweep duration × FFT update rate |
| Parameter discovery | Reads plugin's parameter list directly | User picks targets via DAW automation routing |
| Axis labeling | Auto-derives "20 Hz → 20 kHz log" from plugin metadata | User types labels manually |
| What can be swept | Parameters of the plugin loaded into Plugin Doctor | Anything the DAW can automate (third-party plugin params, send levels, host effects, multiple targets at once) |
| Cross-plugin sweeps | Not possible | Possible — sweep a parameter on a plugin that isn't even the device under test |
| Non-standard sweep shapes | Linear / log auto | User draws any automation curve they want (focus near a resonance peak, exponential, custom) |

The tradeoff is: Plugin Doctor is more convenient and faster for the common case (sweep this knob and measure THD). Our approach is more flexible and reaches further, at the cost of being real-time and requiring DAW setup.

#### Multi-target DAW automation, per host

How users actually link one automation source to multiple plugin targets depends on the DAW:

- **Bitwig:** Modulators / Macro Knobs — native, clean.
- **Ableton Live:** Macro Controls on a Rack — works, requires putting the plugins in racks.
- **REAPER:** Parameter Modulation, or various macro-style controls; multiple lanes can also share the same automation envelope shape.
- **Logic / Pro Tools / Cubase:** typically separate automation lanes that share the same curve — works but more setup.
- **Unify / Gig Performer / JUCE Plugin Host:** graph-host routing, often via macro knobs or direct parameter wiring.

We document the recommended setup per host once we have hands-on testing.

#### Open question: parameter introspection

A future enhancement could read the effect-under-test's parameter list (via VST3 / AU API surfaces JUCE exposes) and auto-label the sweep axis from the plugin's metadata — matching Plugin Doctor's UX. JUCE's `AudioProcessor::getHostedAudioProcessorParameter` exists but only in certain wrapper contexts. Worth investigating after v3; not required for any earlier phase.

### Implementation phases

| Phase | Approach | Tradeoffs |
|---|---|---|
| **v1 (offline)** | User automates sweep over N seconds; analyzer captures full audio buffer; offline post-process slices by time → position bins | Simplest. Works in any DAW. No real-time coordination. |
| **v2 (audio inference)** | Analyzer cross-correlates the pre-effect signal against the loaded `wavetable.wav` frames to infer current position in real time | No WTSynth changes needed. Works across DAWs. Can struggle when adjacent frames are similar. |
| **v3 (CV-style bus, optional)** | WTSynth adds a second output bus carrying position as DC. Analyzer reads from a third input bus. Sample-accurate. | Requires Shane to add an output bus to WTSynth. Tightest sync. |

Start with v1. Layer v2 and v3 only when needed.

### Latency compensation — v1-mandatory

In linear-track DAWs (Ableton, Logic, Reaper, Cubase, etc.) the pre-effect and post-effect signals reach the plugin via separate track-routing paths, and the effect under test introduces its own delay. The two buses are typically *not* sample-aligned at the plugin's input. Without correction, every measurement — FFT bin division, deconvolution, IMD bin checks, alias detection — drifts by however many samples of offset accumulate between the two paths. Sweep plots smear; THD numbers are wrong; Farina IRs blur.

Approaches, applied in priority order:

1. **Manual entry.** A "Pre-Effect Delay (samples)" integer parameter in the plugin's APVTS, exposed in the editor as a number box. The user types the effect's latency (often known from the effect's UI, or derivable). Applied via a `juce::dsp::DelayLine` on the pre-effect (sidechain) bus before any measurement. Always available; the ground truth when host PDC is masking the offset.
2. **Auto-measure via cross-correlation.** FFT-based: 16384-sample capture of raw pre and post on channel 0, DC-removed and Hann-windowed before forward FFT, cross-spectrum `conj(A)*B`, inverse FFT, peak search over positive lags `[0, kXcorrMaxLag)`. Writes its result into the manual-entry parameter via the editor's APVTS path. Triggered by an "Auto" button.
3. **Query the host's reported latency** — JUCE's `AudioProcessor` plumbing exposes plugin-reported latency in some wrapper contexts. Use as a cross-check / sanity readout; some DAWs report this honestly, some don't.

**Both (1) and (2) landed as of 2026-05-13.** The full chain: ring buffers fill continuously in `processBlock` before manual delay is applied, so a measurement returns the absolute effect-induced offset rather than residual. The math was verified against a synthetic self-test (white noise + known delay through the same algorithm path) before the debug surface was removed.

**Important caveat about hosts with PDC.** Ableton (and other DAWs) compensate the sidechain bus internally so that pre and post arrive sample-aligned at the plugin's inputs. With PDC active, Auto correctly reports lag ~0 because the offset has already been removed by the host - there is nothing left to measure. The fallback in that case is manual entry: the user types the effect's reported latency, and our delay line compensates. Auto is genuinely useful when:
- The host has no PDC (graph hosts, some embedded contexts).
- The user has explicitly disabled PDC (Ableton: Options menu > Delay Compensation toggle off).
- The effect under test doesn't report latency to the host, so PDC can't compensate it.

## 8. Key design decisions

### Why JUCE
Shane uses JUCE for WTSynth and Unify; staying in the same ecosystem makes collaboration smoother. JUCE has first-class multi-bus support, built-in FFT (`juce::dsp::FFT`), and good cross-platform plugin scaffolding.

### Why C++20
Wavefield (separate project) already uses C++20. JUCE has supported it since 7.0. No reason to default to a lower standard for new work in 2026. Benefits: `std::span`, `std::ranges`, designated initializers, three-way comparison.

### Why offline first (v1)
Real-time position inference is achievable but harder. Offline post-processing of captured sweeps gets us useful diagnostics with no inter-plugin coordination and no latency-alignment guesswork. Real-time mode layers on top once the offline path works.

### Why universal DAW compatibility from v1
A two-input-bus JUCE plugin maps to main-input + sidechain in VST3/AU automatically — every modern DAW (Ableton, Logic, Reaper, Cubase, Bitwig, Studio One, Pro Tools, FL Studio) supports sidechain routing. A single architecture covers all of them; building a graph-host-only first version would mean a second testing pass and possible re-architecture once we widened scope. Not worth it. The cost is that linear-DAW signal paths introduce variable latency between Pre and Post, which makes §6's latency compensation v1-mandatory rather than deferred.

### Why we're not building a host
Plugin Doctor by DDMF is the established commercial alternative for the "host-the-plugin-and-test-it" model. We're explicitly *not* trying to replicate that. Our differentiation is: in-DAW context, hardware-friendly chain testing, custom Python-defined test signals, and wavetable-position-as-diagnostic-axis sweeps that aren't possible in fixed-signal tools.

## 9. What we're explicitly skipping

- **Python at runtime inside the analyzer** — Python lives in WTSynth's script-runner only; the analyzer reads the file artifacts (WAV, optional JSON) and stays C++-only.
- **Inter-plugin IPC** — host-mediated multi-bus + shared DAW automation is the contract.
- **Real-time network DSP** — out of scope. Different project category.
- **AAX, LV2, VST2, AUv3** — only VST3 + AU + macOS for now. Easy to expand later.
- **CPU profiling of the plugin under test** — Plugin Doctor's territory. We're outside the plugin, can't observe its `processBlock` time directly.
- **Direct plugin parameter introspection** — we don't read the device-under-test's parameters; the user labels the sweep axis manually.

## 13. Background context

For deeper context on decisions and rationale, see the project conversation history. Key reference points:

- **Original idea:** a "2nd plugin" companion to WTSynth that does comparative analysis. Shane's email reply suggested loading `wavetable.wav` directly and using multi-bus routing — both adopted.
- **Why WTSynth's 8-bit format was the bottleneck:** the Python scripts were originally written using stdlib `wave` (which only supports integer PCM, requires struct-packing for ≥16-bit). Switching to `numpy + soundfile` collapsed the binary handling to a one-liner and unlocked float WAV.
- **Why float WAV matters:** measurement-grade diagnostics (Farina deconvolution, low-level THD/IMD, reverb IRs) require dynamic range well below the 8-bit noise floor (~−48 dBFS). Float WAV pushes the floor to ~−150 dBFS — effectively infinite for audio measurement.
- **The "two-plugin DSP test bench" framing:** WTSynth + WTAnalyzer together approximate what Plugin Doctor does, but in a DAW-native, signal-extensible way. That's the value proposition. We are not competing with Plugin Doctor; we occupy an adjacent niche.
